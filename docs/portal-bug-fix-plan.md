# 포털 사용에 영향을 주는 두 버그 수정 계획

- 상태: 구현 및 자동 검증 완료. 실제 모니터 연결·해제 확인은 미실시. 결과는 문서 끝에 기록.
- 작성일: 2026-09-08
- 검토 기준: `b88f507` 및 현재 작업 트리의 Swift 소스
- 사용 환경: 맥북 내장 화면 + 가로 모니터 + 세로 모니터. 포털 위주로 사용하며 단축키와 창 복원은 사용하지 않음.

## 1. 목표와 범위

다음 두 버그를 해결한다.

1. 저장된 화면 배치를 정리한 후 이전 배열 인덱스를 사용하여 앱이 종료되거나 잘못된 배치를 반환하는 문제.
2. 실제 화면 배치가 바뀌었을 때 그 배치에 저장된 포털이 마우스 처리 서비스에 적용되지 않는 문제.

완료 후에는 실제 화면 구성의 인식이 끝났을 때 **현재 배치 ID, 해당 배치의 저장된 포털, 실제 마우스 처리에 사용하는 포털이 일치**해야 한다. 메인 창을 닫고 메뉴 막대에서 실행 중이어도 같은 규칙을 적용한다.

이번 작업에서 제외할 항목:

- 사용자 단축키가 모니터 재연결 후 기본값으로 돌아가는 별도 문제.
- 포털 전체 켜짐/꺼짐 상태의 재실행 간 유지.
- 창 복원 기능의 개선 또는 삭제.
- 포털 이동 좌표 계산, 감지 허용 오차, 키를 누르는 방식 등 입력 알고리즘 변경.
- 배치 보존 기준 변경, 새로운 클라우드 동기화, 외부 패키지 도입.

## 2. 버그 A: 정리 후 이전 인덱스 사용

### 원인과 발생 조건

`DisplayLayoutService.matchOrCreateLayout(for:preserving:)`의 기존 배치 매칭 경로는 다음 순서다.

```swift
if let matchedIndex = layouts.firstIndex(where: { $0.matches(displays: displays) }) {
    currentLayoutID = layouts[matchedIndex].id
    pruneLayouts(preserving: displayLayoutSignatures)
    save()
    return layouts[matchedIndex]
}
```

목표 배치 앞의 항목이 정리되면 `matchedIndex`는 더 이상 목표 배치를 가리키지 않는다.

| 정리 전 목록 | 정리 후 목록 | 현재 결과 | 수정 후 결과 |
| --- | --- | --- | --- |
| `[삭제 대상, 목표 배치]` | `[목표 배치]` | 인덱스 1 접근으로 종료 | 목표 배치 반환 |
| `[삭제 대상, 목표 배치, 보존 배치]` | `[목표 배치, 보존 배치]` | 보존 배치를 잘못 반환 | 목표 배치 반환 |

삭제 대상은 현재 배치가 아니면서 잠금·포털·창 복원 기록이 모두 없는 배치다. 잠금 해제 외에도 마지막 포털 또는 마지막 창 복원 기록의 삭제가 조건을 만들 수 있다. 각 동작 직후 항상 발생한다는 뜻은 아니며, 이후 매칭 및 정리 경로에서 앞 항목이 실제로 삭제되어야 한다.

현재 앱의 호출 경로는 `ContentView.onAppear`와 화면 변경 알림이다. 따라서 화면 연결·해제뿐 아니라 메인 화면이 나타날 때도 노출될 수 있다.

`save()`가 잘못된 접근보다 먼저 호출되지만, 내부의 `UserDefaults` 저장 완료를 보장하는 것은 아니다. 재실행 복구를 수정 대신 사용하지 않는다. 잘못된 배치 반환 시 `currentLayoutID` 자체는 목표 배치 ID이며, 첫 화면 선택 등 반환값을 사용하는 부분이 잘못될 수 있다. 단축키 초기화에 넘기는 화면 변환은 현재 화면의 ID·좌표·순서를 유지하고 이름만 적용하므로, 이 문제로 단축키 대상 화면까지 바뀐다고 확대 해석하지 않는다.

### 제안 수정

인덱스 대신 매칭한 `DisplayLayout` 값을 먼저 보관하고, 정리 후 고유 ID로 다시 찾는다. 새 배치를 생성하는 경로와 동일한 방식이며, 배열 위치에 의존하지 않는다.

```swift
// 제안 코드이며 아직 적용하지 않음.
if let matchedLayout = layouts.first(where: { $0.matches(displays: displays) }) {
    currentLayoutID = matchedLayout.id
    pruneLayouts(preserving: displayLayoutSignatures)
    save()
    return layouts.first(where: { $0.id == matchedLayout.id }) ?? matchedLayout
}
```

- 현재 배치를 먼저 지정하여 삭제 대상에서 보호하는 순서를 유지한다.
- 정리와 저장을 유지한다. 정리를 제거하거나 배열 인덱스를 임의로 보정하지 않는다.
- 기존 배치·포털의 ID, 이름, 잠금 상태, 저장 형식은 유지한다.
- 새로운 배치를 생성하는 경로는 현재도 ID로 반환하므로 불필요하게 변경하지 않는다.

## 3. 버그 B: 배치 전환 시 포털 미적용

### 원인과 재현

배치별 포털의 원본은 `DisplayLayout.portals`다. 실제 입력 처리는 `PortalService.portals`와 콜백용 상태를 사용한다.

현재 `syncToPortalService()`는 포털 추가·수정·삭제·개별 활성화 변경 때 호출되지만, 화면 배치를 인식하고 전환하는 경로에서는 호출되지 않는다. `PortalService`의 화면 변경 처리는 화면 좌표 캐시만 갱신한다.

재현 순서:

1. 화면 3개 구성 A에서 포털 A를 설정한다.
2. 화면 2개 구성 B로 바꾸고 포털 B를 설정한다.
3. 구성 A로 돌아온다.
4. 현재 배치는 A이고 저장된 포털도 A인데, 실제 서비스의 포털은 B로 남는다.

이는 실제 서비스 메서드에 모의 화면 데이터를 넣어 확인한 상태 불일치다. 물리적 모니터 연결·해제 및 커서 이동까지 재현한 것은 아니다.

### 제안 수정: 앱 수명 동안 유지되는 공통 적용 경로

메인 화면에 동기화 호출만 추가하면 화면의 생명주기에 의존한다. 메뉴 막대에서 계속 쓰는 용도를 고려하여 화면 인식·배치 선택·포털 적용을 앱 수명 동안 유지되는 작은 조정 서비스로 모은다.

제안 이름: `DisplayConfigurationCoordinator` (`@MainActor`). 이름은 구현 시 프로젝트 관례에 맞춰 조정 가능하다.

역할은 다음으로 제한한다.

1. 앱 시작과 `NSApplication.didChangeScreenParametersNotification`을 받는다.
2. 현재 활성 화면 목록을 조회한다.
3. 기존 배치 매칭·보존 로직으로 실제 현재 배치를 결정한다.
4. 해당 배치의 포털과 같은 화면 목록에서 만든 좌표 캐시를 `PortalService`에 적용한다.

소유자는 `AppDelegate`로 두며, 알림 등록은 앱 실행 중 하나만 유지한다. 시작·종료는 중복 호출해도 안전해야 한다. `ContentView`는 배치를 표시하고 사용자가 조회할 배치를 선택하는 역할을 유지한다.

### 적용 규칙

- 기존 배치로 돌아오면 그 배치의 포털을 적용한다. 이전 실행에서 로드한 전역 `portalPairs` 값을 계속 사용하지 않는다.
- 새 배치 또는 포털이 없는 배치는 빈 포털 목록을 적용한다. 이전 배치의 포털을 새 배치에 복사하지 않는다.
- 비어 있는 활성 화면 조회 결과로 배치를 만들거나 저장 목록을 정리하지 않는다. 일시적 조회 실패 시 마지막 정상 배치를 보존하고 다음 화면 변경 또는 명시적 새로고침에서 재확인한다.
- 화면 변경 알림이 연속되면 마지막 알림으로부터 0.5초 후 실제 화면을 다시 조회하는 순수 디바운스를 사용한다. `requiredStableCount`, `pendingSignature`, `stableCount`, `pendingDisplays`는 제거한다. 기존 3회 경로는 실행 가능하나 동일 알림 반복 횟수에 의존하므로 안정성의 근거로 사용하지 않는다. UI 측 타이머와 서비스 측 캐시 갱신 지연을 중복 운영하지 않는다.
- 포털 목록과 화면 좌표 캐시는 같은 화면 스냅샷으로 갱신한다. `PortalEventTapState`에 한 번의 잠금으로 두 상태를 반영하는 경로를 마련하여, 새 포털과 이전 좌표가 섞인 콜백 상태를 피한다.
- `PortalService.portals`의 기존 `didSet`도 콜백을 갱신하므로, 일괄 적용 중 중간 상태를 공개하지 않도록 내부 적용 메서드를 정리한다. 일반 포털 편집 때의 기존 갱신 동작은 유지한다.
- 포털 설정 적용 때문에 이벤트 감시를 중지·재생성하지 않는다. 현재 포털 서비스가 꺼져 있다면 설정만 갱신하고 임의로 켜지 않는다.
- 앱 시작 시 최초 화면 인식 및 포털 적용을 수행한 뒤 기존 조건에 따라 입력 감시를 시작한다. 권한이 없어 감시를 시작하지 못해도 배치 목록 표시는 가능해야 한다.
- 화면에서 다른 저장 배치를 클릭하는 것은 조회 동작이다. `selectedLayoutID` 변경만으로 실제 적용 포털을 바꾸지 않는다. 실제 현재 배치와 조회 중인 배치를 구분한다.
- 창 복원 기록이 있는 배치를 보호하기 위한 기존 `preserving` 정보는 공통 경로에도 전달한다. 창 복원 자체를 실행하거나 활성화하지 않는다.
- 화면 변경 처리가 UI에서 빠지더라도 기존 화면 목록 갱신과 단축키 초기화 호출이 누락되지 않도록 이동한다. 단축키 초기화 알고리즘은 수정하지 않는다.
- 설정 씬의 `PortalSettingsView`도 현재 배치의 포털을 표시하고 삭제·토글은 `DisplayLayoutService`로 전달한다. 복수 삭제 시 삭제 전 ID들을 확보하여 인덱스 이동 문제도 피한다.
- 호출되지 않는 `syncFromPortalService()`는 제거한다. 배치 원본에서 런타임으로 적용하는 방향을 유지한다. 현재 참조가 없는 `PortalEditorView`의 기능 개편은 제외한다.

### 구현 범위를 작게 유지하는 방법

- 배치 모델과 매칭·정리 로직은 `DisplayLayoutService`에 남긴다.
- `DisplayConfigurationCoordinator`는 기존 서비스를 연결하고 알림·예약 실행을 소유하는 역할만 갖는다.
- 테스트용 화면 제공자와 적용 결과 수신자를 주입할 수 있도록 최소한의 생성자 또는 클로저를 제공한다. 전체 프로젝트의 싱글턴 구조를 개편하지 않는다.
- 공통 경로로 옮긴 UI 알림과 `PortalService`의 독립적인 화면 캐시 갱신은 제거하거나 공통 경로로 위임한다. 같은 알림으로 배치 선택·저장이 중복 수행되지 않게 한다.

## 5. 검증 계획

### 자동 테스트

| 구분 | 시나리오 | 기대 결과 |
| --- | --- | --- |
| A-1 | `[삭제 대상, 목표 배치]`에서 목표 매칭 | 정상 반환, 반환 ID와 현재 배치 ID가 목표와 일치 |
| A-2 | `[삭제 대상, 목표 배치, 잠긴 다른 배치]`에서 목표 매칭 | 다른 배치가 아닌 목표 반환, 잠긴 배치 보존 |
| A-3 | 목표보다 앞에 여러 삭제 대상 존재 | 삭제 개수와 관계없이 동일한 목표 반환 |
| A-4 | 잠긴 배치·포털 있는 배치·창 기록 있는 배치 존재 | 기존 보호 정책 유지 |
| A-5 | 삭제 대상 없음 또는 신규 배치 생성 | 기존 정상 동작 유지 |
| B-1 | 포털 A가 있는 배치 A → 포털 B가 있는 B → A | 각 단계에서 현재 배치와 런타임 포털 ID가 일치 |
| B-2 | 포털 있는 A → 포털 없는 B → A | B에서 런타임 포털은 빈 목록, A 복귀 시 A 복원 |
| B-3 | 저장된 전역 포털은 B, 앱 시작 시 실제 화면은 A | 입력 감시 시작 전 A 적용 |
| B-4 | 메인 화면을 만들지 않고 화면 변경 알림 전달 | 조정 서비스만으로 배치와 포털 갱신 |
| B-5 | 여러 화면 변경 알림이 짧게 연속 발생 | 마지막 실제 화면 구성을 적용, 중복 관찰·예약 누적 없음 |
| B-6 | 화면 조회가 일시적으로 빈 목록 반환 | 기존 저장 배치 보존, 이후 유효 조회에서 정상 적용 |
| B-7 | 실제 배치는 A인 상태에서 UI로 B 조회 | 실제 적용 포털은 A 유지 |
| B-8 | 포털 감시가 꺼진 상태에서 화면 변경 | 설정은 갱신되지만 감시는 꺼진 상태 유지 |
| B-9 | 조정 서비스 시작·종료·재시작 및 해제 | 중복 알림 처리 없음, 종료 후 예약 작업 미실행. 예약 작업은 UI 클로저를 받거나 보관하지 않음 |
| B-10 | 포털 편집 및 일괄 화면 전환 | 포털 편집 반영 유지, 콜백에서 포털·화면 캐시의 일관성 유지 |
| B-11 | 설정 씬의 삭제·토글 경로 실행 후 배치 전환 및 저장소 재로딩 | 삭제한 포털이 되살아나지 않고 비활성화가 유지됨. 복수 삭제도 올바른 ID만 삭제 |

배치 A와 B는 각기 다른 실제 화면 좌표 조합으로 구성한다. 포털 이름만 비교하지 않고 ID와 선분의 화면 식별 정보를 확인한다. 보존이 필요한 배치는 포털 또는 잠금을 설정하여 테스트 중 의도치 않게 정리되지 않도록 한다.

테스트는 실제 손쉬운 사용 권한, 전역 입력 감시 또는 마우스 이동을 요구하지 않도록 구성한다. 저장 검증은 별도 `UserDefaults` suite를 사용한다. 기존 싱글턴을 사용하는 테스트가 필요한 경우 변경하는 모든 설정 키와 런타임 상태를 복원한다. 크래시 재현 테스트는 수정 전 실행 시 테스트 프로세스를 종료시킬 수 있으므로, 실패 재현은 별도 실행으로 분리하고 수정 후 전체 테스트에 포함한다.

### 실제 사용 확인

구현 이후 자동 테스트와 별도로 다음을 확인한다.

1. 맥북 + 가로 + 세로 화면에서 포털을 설정하고 커서 이동이 정상인지 확인.
2. 모니터 하나를 분리한 구성에서도 별도 포털을 설정한 후 원래 구성으로 복귀하여 원래 포털이 적용되는지 확인.
3. 메인 창을 닫고 같은 전환을 반복하여 메뉴 막대 실행 중에도 적용되는지 확인.
4. 앱을 종료한 뒤 다른 저장된 화면 구성에서 재실행하여 처음부터 올바른 포털을 사용하는지 확인.
5. 포털을 꺼 둔 실행 세션에서 연결·해제가 포털 감시를 다시 켜지 않는지 확인.

물리적 모니터 조작이 필요한 항목은 자동 테스트 통과만으로 완료 처리하지 않는다. 직접 확인하지 못한 항목은 구현 결과에 미확인으로 기록한다.

- 단순 마우스 이동 경로에 화면 조회, 배치 매칭, 디스크 저장이 추가되지 않았는지 확인.

## 6. 호환성과 주의점

- 배치 저장 JSON과 `portalPairs` 저장 키는 유지한다. 현재 배치의 포털을 적용할 때 기존 전역 저장 값도 같은 포털로 갱신하여 재실행 상태를 맞춘다.
- 최초 공개 소스 커밋부터 배치 모델이 있으므로 가상의 전역 전용 구버전을 위한 자동 마이그레이션은 추가하지 않는다. 다만 이력만으로 모든 사용자 데이터가 일관적이라고 단정하지 않는다. 기존 설정 씬의 직접 수정도 불일치를 만들 수 있다. 최초 배치 적용 전에 원래 `portalPairs` 데이터를 별도 로컬 키에 한 번 보관하고, 이후 덮어쓰지 않는다. 이를 현재 배치에 역으로 복사하거나 자동 병합하지 않는다.
- 화면을 모두 다시 확인하기까지의 안정화 대기 자체를 없애지는 않는다. 연결 순간부터 지연이 전혀 없다는 보장은 목표가 아니다.
- 배치 선택의 의미를 바꾸지 않는다. 사용자가 과거 배치를 조회하는 행위와 실제 화면 구성의 변경을 혼동하지 않는다.
- 기존 `.omc/` 등 작업 트리의 다른 파일은 이번 작업 대상이 아니다.

## 8. 검토 의견에 대한 판단 및 작업 단위

- P1: 수용. 설정 씬의 두 번째 작성자를 수정하지 않으면 설정이 되살아나는 회귀가 발생한다.
- P2: 수용. 미사용 역방향 동기화 함수를 제거한다.
- P3: 단순화 수용. 3회 경로가 실행 불가능하다는 판단은 하지 않는다. 순수 디바운스로 바꾸고 관련 테스트도 목적 중심으로 대체한다.
- P4: 생명주기 방어 수용. 창 닫힘과 뷰 즉시 소멸을 동일시하거나 메모리 안전성 문제로 단정하지 않는다. 예약 작업에서 UI completion 자체를 없앤다.
- P5: 조사 범위 축소는 수용하나 전역 전용 또는 불일치 데이터의 부재는 확정하지 않는다. 로컬 복구 사본으로 기존 데이터를 보존한다.
- 구현 중 P5를 추가 검증한 결과, 기존 `PortalService.migrateIfNeeded()`는 전역 포털만 변환하며 배치 내부 포털에는 적용되지 않는다. 구형 배치의 포털이 `legacyDisplayID`를 보관한 상태에서 실제 화면 ID가 바뀌면 새 적용 경로에서 커서 목적지 계산이 실패하는 테스트를 재현했다. 매칭된 배치의 저장된 `DisplaySnapshot.displayID`와 좌표로 선분을 변환하고 같은 배치에 저장한다. 포털과 선분 UUID는 유지하며, 대응하는 저장 화면 정보가 없는 선분은 추측하여 변환하지 않는다.
- A의 반환 방식은 ID 재조회로 통일하고, 크래시 회귀 테스트에는 불필요한 목록 길이 단언을 넣지 않는다.

예정 커밋: (1) 검토 반영 계획서, (2) 버그 A 및 회귀 테스트, (3) 버그 B·설정 씬 일관성·디바운스 및 회귀 테스트. 추가 수정이 필요하면 독립된 후속 커밋으로 기록한다. 사용자 요청에 따라 로컬 커밋까지 수행하며 원격 push나 PR 생성은 이 작업의 완료 조건이 아니다.

## 9. 구현 결과 및 검증 기록

브랜치: `fix/portal-layout-transitions`

- 검토 반영 계획서는 `f3805e1`, 버그 A 수정은 `9405b00`에 기록했다. 버그 B의 관련 변경은 별도 커밋으로 묶는다.

- B: `AppDelegate`가 조정 서비스를 소유하며 시작 시 적용을 입력 감시보다 먼저 수행한다. 화면 알림은 한 곳에서 디바운스하고 실행 시 다시 조회한다. UI는 더 이상 예약 completion을 제공하지 않는다.
- 설정 씬의 삭제·토글은 배치 저장소를 수정한다. 복수 삭제는 ID 집합으로 처리한다. 미사용 `syncFromPortalService()`와 기존 배치 안정화 상태·타이머를 제거했다.
- 포털과 화면 좌표를 이벤트 콜백 상태에 한 번의 잠금으로 반영한다. 화면 전환에서 이벤트 탭을 재생성하거나 켜지 않는다.
- `portalPairsBeforeLayoutSync` 키에 최초 적용 전 전역 포털 데이터의 로컬 사본을 보관한다. 기존 사본은 후속 적용·재시작에서 덮어쓰지 않는다. 이 사본은 자동으로 복원되거나 원본 배치에 병합되지 않는다.
- 기존 배치 안의 구형 선분은 저장된 화면 ID와 좌표로 변환한다. 실제 화면 ID가 바뀐 입력에서 변환 전 목적지 계산 실패와 변환 후 성공을 확인했으며, 포털·선분 UUID 및 저장 후 재로딩도 검증했다.
