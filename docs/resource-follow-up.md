입력 이벤트 탭의 평균 지연 통계가 약 85ms로 조회됐다. 이후 약 10초간 반복 조회에서도 값이 변하지 않아, 현재 입력 부하를 반영하는지 확인되지 않았다. 실제 포털 이동 지연으로 단정하지 말고, 다음 검사에서 마우스를 움직이며 다시 측정한다. `CGGetEventTapList` 조회는 최소·최대 지연 통계를 재설정하므로 측정 방법도 기록한다.

## 며칠간 사용 방법

- 설치본 하나만 실행하고, 창은 닫아도 되지만 포털을 쓰는 동안 앱을 Quit하지 않는다.
- 평소처럼 포털을 사용한다. 자연스럽게 발생하는 모니터 연결·해제, 잠자기·깨우기, 설정 창 열기·닫기도 포함한다.
- 앱 종료·재실행, 맥 재부팅, 앱 업데이트가 있으면 대략적인 시각을 기록한다. 재시작 전후는 별도 측정 구간으로 취급한다.
- 커서 끊김·잘못된 이동·포털 미작동·팬 소음·발열·배터리 급감이 느껴지면 시각과 직전 행동을 기록한다. 원인은 측정 전까지 MousePortal로 단정하지 않는다.
- 권장 재점검 시점: 3–7일 사용 후. 그 전에 이상이 생기면 즉시 검사한다. 문제 확인을 위해 설정을 지우거나 앱을 재설치할 필요는 없다.

## 후속 검사 절차

1. 실행 경로, 현재 PID, 앱 버전과 실행 경과 시간을 다시 확인한다. 중복 프로세스가 없는지 확인하고 이전 PID를 그대로 사용하지 않는다.
2. 대기 상태에서 CPU·메모리·스레드 수를 1–2분 관찰한다. 메모리는 최초 기록과 같은 footprint 지표로 비교한다.
3. 마우스를 계속 움직이고 포털을 양방향으로 여러 번 통과하는 동안 1–2분 재측정한다. 대기 상태와 입력 처리 중 수치를 구분한다.
4. 앱 창 열기·닫기와 모니터 전환 전후의 값을 비교한다. 작업을 마친 뒤 대기로 돌아왔을 때 메모리가 계속 증가하는지 확인한다. 단순 캐시 증가나 일시적인 최고값과 지속 증가를 구분한다.
5. 잠자기 복귀·모니터 재연결 후 포털이 정상 작동하는지, 삭제·비활성화한 포털이 되살아나지 않는지 확인한다.
6. 네트워크 소켓을 다시 조회한다. 발견되면 대상과 발생 조건을 조사하되, 소켓 부재만으로 통신이 전혀 없다고 결론 내리지 않는다.
7. 입력 이벤트 탭 활성 상태와 지연 통계를 실제 입력 중 확인한다. 이상이 재현되면 짧은 스택 샘플이나 Instruments 분석으로 원인을 좁힌다.
8. 필요하면 에너지 영향과 wakeup을 별도 측정한다. CPU 사용량만으로 배터리 소비량을 확정하지 않는다.

읽기 전용 기본 명령 예시 (확인한 설치본 PID로 `<PID>`를 바꿔 실행):

```sh
pgrep -fl MousePortal
ps -p <PID> -o pid,etime,%cpu,rss,time,state,command
top -l 31 -s 2 -pid <PID> -stats pid,command,cpu,mem,threads,ports,pageins,time
vmmap -summary <PID>
lsof -nP -a -p <PID> -i
```

`top`의 첫 CPU 표본은 구간 비교에서 제외한다. 후속 구간 표본과 `vmmap` 결과를 중심으로 비교한다. 진단 중 앱 종료, 설정 변경, 코드 수정이 필요하면 별도 작업으로 다룬다.

## 판단 기준과 한계

- 대기 중 CPU가 반복적으로 높거나, 같은 작업을 반복할수록 대기 시 메모리·스레드·포트 수가 계속 증가하면 추가 조사한다.
- 입력 처리 중 순간적인 CPU 상승만으로 결함이라고 판단하지 않는다. 지속 시간, 커서 체감 지연, 대기 복귀 여부를 함께 본다.
- 며칠 뒤 단일 측정은 그 시점의 상태일 뿐이다. 누적 사용 중 최대 부하나 과거의 일시적 문제를 복원할 수 없다. 누수 의심 시 여러 시점의 비교 또는 별도 프로파일링이 필요하다.
- 현재 결론은 **짧은 대기 측정에서 리소스 과다 사용 징후가 없었다**는 범위로 한정한다.
